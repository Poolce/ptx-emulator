## Слайд 2 — Проблема и мотивация (1 мин)

**Текст на слайде:**
- CUDA доминирует в HPC, AI, научных расчётах
- Отладка требует **физического GPU**: Nsight, Compute Sanitizer — недоступны в CI/облаке
- Аппаратные счётчики — агрегаты уровня SM, **нет метрик уровня инструкций PTX**

**Картинка:** стек компиляции CUDA (`cuda_stackbw.png`) — схема: `.cu → NVVM → PTX → SASS → GPU`

**Что говорить:**
> «GPU-ускорители стали основой высокопроизводительных вычислений. Однако отладка CUDA-ядер по-прежнему требует реального GPU — официальные инструменты NVIDIA недоступны в облачных CI-средах и виртуальных машинах. При этом аппаратные счётчики дают лишь статистику на уровне SM, но не позволяют увидеть, какая конкретная инструкция PTX является узким местом. PTX — это стабильный публичный контракт NVIDIA, который компилятор гарантирует между поколениями GPU. Именно на этом уровне мы строим эмулятор.»

## Слайд 5 — Архитектура: LD\_PRELOAD-перехват (1.5 мин)

**Картинка:** схема `ldpreload_arch.png` — диаграмма: CUDA-приложение → PLT → `libemuruntime.so` (вместо `libcudart.so`) → Parser → Executor → Profiler

**Текст на слайде:**
```
export LD_PRELOAD=libemuruntime.so
cuemu ./binary
```
- `__cudaRegisterFatBinary` → вызов `cuobjdump --dump-ptx`
- `cudaLaunchKernel` → диспетчер блока
- `cudaMalloc/Free/Memcpy` → управление памятью эмулятора

**Что говорить:**
> «Механизм перехвата — ключевая архитектурная идея. Динамический загрузчик Linux разрешает символы по правилу первого совпадения: поместив libemuruntime.so в LD\_PRELOAD, мы перехватываем все вызовы CUDA Runtime до того, как они достигнут оригинальной libcudart. Бинарный файл приложения не модифицируется — достаточно однострочного запуска cuemu ./binary. При перехвате __cudaRegisterFatBinary эмулятор вызывает утилиту cuobjdump и извлекает PTX-текст прямо из секции .nv_fatbin ELF-файла.»

## Слайд 7 — Формальная семантика SIMT-исполнения (1.5 мин)

**Текст на слайде:**

Варп: W = ⟨T, M, PC, R, S⟩, где M ∈ B^32 — маска исполнения

Ключевой инвариант:
> **Исполнитель обязан игнорировать потоки с M[i]=0 при записи результата**

Семантика `add.u32 %rd, %ra, %rb`:

    R'[t][u32][d] = (R[t][u32][a] + R[t][u32][b]) mod 2^32,  ∀t ∈ active(M)

**Что говорить:**
> «Всё исполнение построено вокруг маски активных потоков. Варп — это 32 потока, исполняющих одну инструкцию. Маска задаёт, какие из них реально записывают результат. Это не просто флаг — нарушение инварианта приводит к семантической ошибке: неактивный поток не должен изменять ни регистры, ни память. Регистровый файл организован как вектор на поток, все значения хранятся в uint64_t, доступ через bit_cast без нарушения строгого псевдонимирования C++20.»

## Слайд 8 — PDOM-реконвергенция (2 мин)

**Текст на слайде:**

Проблема: `@%p bra $L` → часть потоков берёт переход, часть нет → **дивергенция варпа**

Алгоритм PDOM\_Diverge:
```
M_taken = M ∧ P
M_not   = M ∧ ¬P
push(S, {PC+1, M_not, is_conv=false})   ← отложить ветку продолжения
M ← M_taken;  PC ← offset($L)          ← исполнить ветку перехода
```

Теорема: IPDOM(N) — точка реконвергенции, через которую проходят **все** пути из N до exit

**Схема (нарисовать на слайде):** стек фреймов, две ветки, восстановление маски в IPDOM

**Что говорить:**
> «Дивергенция — главная сложность в SIMT-исполнении. Когда потоки варпа расходятся на условном переходе, нужно исполнить обе ветки последовательно, не потеряв ни одного потока. Стратегия: откладываем ветку продолжения на стек как фрейм ожидания, немедленно исполняем ветку перехода. Точка слияния — непосредственный постдоминатор — обнаруживается динамически, когда ветка перехода завершается безусловным прыжком вперёд. Алгоритм PDOM_Merge записывает в стек фрейм реконвергенции с восстановленной объединённой маской. Доказано: все потоки встретятся в IPDOM, ни одна инструкция активного пути не пропускается. Поддерживаются вложенные дивергенции произвольной глубины — стек растёт на 2 фрейма на каждый уровень.»

## Слайд 9 — Система профилирования и метрики (1.5 мин)

**Текст на слайде — 5 метрик:**

| Метрика | Формула | Смысл |
|---|---|---|
| `branch_efficiency` | η = popcount(M)/32 | Доля активных потоков |
| `bank_conflicts` | C = max_b\|{t: bank(ea(t))=b}\| − 1 | Конфликты банков shared mem |
| `global_mem_transactions` | T = \|{⌊ea(t)/128⌋}\| | Кол-во кэш-транзакций |
| `global_coalescing` | κ = T_ideal/T_actual | Коэфф. слияния памяти |
| `write_ops` | Σ popcount(M_k) | Давление на регистровый файл |

**Что говорить:**
> «Профилировщик реализован через кодогенерацию. JSON-манифест задаёт, какие метрики собирать для каждой мнемоники. Autogen.py генерирует методы Profile() с атрибутом [[unlikely]] — на горячем пути при выключенном профилировании стоимость проверки флага нулевая. Буферизация — per-warp, сброс в общий буфер один раз по завершении блока, что минимизирует синхронизацию.»
